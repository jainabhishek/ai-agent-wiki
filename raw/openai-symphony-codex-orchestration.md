## Introduction

- About six months before the post, the team decided that every line in an
  internal productivity-tool repository would be generated by Codex (no
  human-written code). They redesigned the workflow around this: an
  agent-friendly repo, automated tests and guardrails, Codex as a teammate. This
  journey is the subject of OpenAI's earlier "harness engineering" post.
- The next bottleneck was context switching. Symphony is an agent orchestrator
  that turns a project-management board (Linear) into a control plane for coding
  agents: every open task gets an agent, agents run continuously, humans review
  results.
- Headline result (self-reported): a 500% increase in landed pull requests on
  some teams.

## The ceiling of interactive coding agents

- Coding agents in web apps or CLIs are still interactive tools. Each engineer
  opened a few Codex sessions, assigned tasks, reviewed, steered, repeated.
- Most people could manage three to five sessions before context switching hurt;
  beyond that productivity dropped (forgetting which session did what, nudging
  agents across terminals, debugging stalled long tasks).
- Bottleneck: human attention. The authors compare it to assigning human
  engineers to micromanage a team of capable junior engineers.

## A shift in perspective

- Sessions and PRs are a means to an end; software work is organized around
  deliverables (issues, tasks, tickets, milestones).
- Idea: stop supervising agents directly and let them pull work from the task
  tracker. Symphony is "a written spec that functions as a supervisor".

## Turning our issue tracker into an agent orchestrator

- Any open task should be picked up and completed by an agent. Each open Linear
  issue maps to a dedicated agent workspace. Symphony watches the board and
  ensures each active task has an agent running until done; it restarts crashed
  or stalled agents and picks up new work.
- Ticket statuses drive the workflow; Linear is used as a state machine.
- Work is decoupled from sessions and PRs: an issue can produce several PRs
  across repos, or be pure investigation with no code change.
- Large units of work: an agent can analyze the codebase, Slack, or Notion and
  produce an implementation plan; once approved, it generates a tree of tasks
  with stages and dependencies. Agents start only unblocked tasks, so the DAG
  executes in parallel. Example: a React upgrade marked blocked on a Vite
  migration started only after the migration finished.
- Agents file new issues for out-of-scope improvements they notice
  (performance, refactoring, architecture); many are later picked up by agents.
- Kicking off ambiguous work becomes cheap; wrong results are still
  information. The orchestrator runs on devboxes continuously; one engineer made
  three significant changes from the Linear phone app.

## An increase in exploration from working this way

- Some OpenAI teams saw landed PRs rise 500% in the first three weeks. Linear's
  founder reported a spike in new workspaces at release.
- Perceived cost of each change drops; speculative tasks become trivial.
- Product managers and designers file feature requests directly and get back a
  review packet including a video walkthrough of the feature in the real product.
- In large monorepos Symphony watches CI, rebases, resolves conflicts, retries
  flaky checks, and shepherds changes; by the `Merging` state the team has high
  confidence the change will land without babysitting.

## Progress comes with new, different problems

- Ticket-level assignment loses mid-flight nudging; some outputs missed
  completely. Response: add guardrails and skills rather than patch results by
  hand. New harness capabilities followed: end-to-end tests, driving the app
  through Chrome DevTools, QA smoke tests, better documentation of "what good
  looks like".
- Not every task fits: ambiguous problems and judgment-heavy work still use
  interactive Codex sessions.
- Treating agents as rigid nodes in a state machine did not work. Early versions
  only asked Codex to implement the task; Codex could also open multiple PRs and
  address review feedback. The team gave it tools (`gh` CLI, skills to read CI
  logs) and broader tasks (closing old PRs, reports on completed vs. abandoned
  work). They moved to giving agents objectives instead of strict transitions,
  like a manager assigning a goal.

## Using Symphony to build Symphony

The repository is essentially a `SPEC.md` ("Symphony Service Specification",
Status: Draft v1, language-agnostic). The post embeds most of the spec. Condensed:

### Spec §1 Problem statement

A long-running service that reads work from an issue tracker (Linear in this
version), creates an isolated workspace per issue, and runs a coding-agent
session in it. Four problems solved: repeatable daemon workflow instead of
scripts; per-issue workspace isolation; workflow policy kept in-repo
(`WORKFLOW.md`) and versioned with code; observability for concurrent runs.
Implementations must document their trust and safety posture; the spec does not
mandate one approval, sandbox, or operator-confirmation policy. Boundary:
Symphony is a scheduler/runner and tracker reader; ticket writes (state
transitions, comments, PR links) are done by the agent with its tools. A
successful run may end at a handoff state such as `Human Review`, not `Done`.

### Spec §2 Goals and non-goals

Goals: poll on a fixed cadence and dispatch with bounded concurrency; one
authoritative orchestrator state; deterministic per-issue workspaces preserved
across runs; stop runs whose issues become ineligible; exponential-backoff
recovery; runtime behavior from repo-owned `WORKFLOW.md`; structured logs;
restart recovery without a persistent database. Non-goals: rich web UI or
multi-tenant control plane; a prescribed dashboard; a general workflow engine;
built-in ticket/PR editing logic; mandating sandbox controls beyond the agent and
host OS; one default approval posture.

### Spec §3 System overview

Components: `Workflow Loader` (parses `WORKFLOW.md` YAML front matter + prompt
body → `{config, prompt_template}`), `Config Layer` (typed getters, defaults,
`$VAR` indirection, validation), `Issue Tracker Client`, `Orchestrator` (poll
tick, in-memory state, dispatch/retry/stop/release), `Workspace Manager`,
`Agent Runner` (launches the coding-agent app-server client), optional `Status
Surface`, `Logging`. Layers: Policy (repo), Configuration, Coordination,
Execution, Integration (Linear adapter), Observability. External dependencies:
tracker API, local filesystem, optional Git, a coding-agent executable that
speaks a JSON-RPC-like app-server protocol over stdio, host auth.

### Spec §4 Domain model

Entities: Issue (`id`, `identifier` e.g. `ABC-123`, `title`, `description`,
`priority` — lower is higher, `state`, `branch_name`, `url`, `labels`
lowercased, `blocked_by`, `created_at`, `updated_at`); Workflow Definition;
Service Config; Workspace (`path`, `workspace_key`, `created_now`); Run Attempt
(`attempt` null on first run); Live Session (`session_id` =
`<thread_id>-<turn_id>`, token counters, `turn_count`); Retry Entry
(`due_at_ms`, `error`); Orchestrator Runtime State (`running`, `claimed`,
`retry_attempts`, `completed`, `codex_totals`, `codex_rate_limits`). Workspace
key: replace any character outside `[A-Za-z0-9._-]` with `_`. States compared
lowercase.

### Spec §5 Workflow specification (repository contract)

- `WORKFLOW.md` from an explicit runtime setting, else the process cwd; read
  failure → `missing_workflow_file`.
- Front matter between `---` lines must be a map; body is the prompt template.
  Top-level keys: `tracker`, `polling`, `workspace`, `hooks`, `agent`, `codex`;
  unknown keys ignored; extensions such as `server.port`.
- `tracker`: `kind` (`linear`), `endpoint` (default
  `https://api.linear.app/graphql`), `api_key` (literal or `$VAR`, canonical
  `LINEAR_API_KEY`), `project_slug`, `active_states` (default `Todo`,
  `In Progress`), `terminal_states` (default `Closed`, `Cancelled`, `Canceled`,
  `Duplicate`, `Done`).
- `polling.interval_ms` default `30000`. `workspace.root` default
  `<system-temp>/symphony_workspaces`.
- `hooks`: `after_create` (failure aborts creation), `before_run` (failure
  aborts the attempt), `after_run` and `before_remove` (failure logged and
  ignored); `timeout_ms` default `60000`.
- `agent`: `max_concurrent_agents` default `10`, `max_turns` default `20`,
  `max_retry_backoff_ms` default `300000`, `max_concurrent_agents_by_state`.
- `codex`: `command` default `codex app-server` (launched via `bash -lc` in the
  workspace); `approval_policy`, `thread_sandbox`, `turn_sandbox_policy` are
  pass-through Codex values (inspect with
  `codex app-server generate-json-schema --out <dir>`); `turn_timeout_ms`
  `3600000`, `read_timeout_ms` `5000`, `stall_timeout_ms` `300000` (≤0
  disables stall detection).
- Prompt template: strict (Liquid-compatible) rendering; unknown variables or
  filters fail. Inputs `issue` and `attempt`. Empty body may fall back to a
  minimal default prompt; parse failures must not silently fall back.
- Errors: `missing_workflow_file`, `workflow_parse_error`,
  `workflow_front_matter_not_a_map`, `template_parse_error`,
  `template_render_error`. File/YAML errors block new dispatch; template errors
  fail only that attempt.

### Spec §6 Configuration

Precedence: path selection → front matter → `$VAR` indirection → defaults.
Dynamic reload is required: watch `WORKFLOW.md`, re-apply without restart;
in-flight sessions need not restart; invalid reloads keep the last known good
config and emit an operator-visible error. Preflight validation at startup
(fail startup) and before each dispatch tick (skip dispatch, keep
reconciliation). Extensions: `worker.ssh_hosts`,
`worker.max_concurrent_agents_per_host`, `server.port`.

### Spec §7 Orchestration state machine

Only the orchestrator mutates scheduling state. Internal claim states:
`Unclaimed`, `Claimed`, `Running`, `RetryQueued`, `Released`. A worker may run
back-to-back turns on the same thread while the issue stays active, up to
`agent.max_turns`; the first turn gets the full prompt, continuation turns get
only continuation guidance. After a normal exit the orchestrator schedules a
~1 s continuation retry to re-check the issue. Run-attempt phases:
`PreparingWorkspace`, `BuildingPrompt`, `LaunchingAgentProcess`,
`InitializingSession`, `StreamingTurn`, `Finishing`, `Succeeded`, `Failed`,
`TimedOut`, `Stalled`, `CanceledByReconciliation`. Reconciliation runs before
dispatch on every tick; restart recovery is tracker- and filesystem-driven.

### Spec §8 Polling, scheduling, reconciliation

Tick: reconcile → validate → fetch candidates → sort → dispatch while slots
remain → notify. Eligible only if required fields exist, state is active and not
terminal, not running or claimed, global and per-state slots free, and (for
`Todo`) no non-terminal blocker. Sort: `priority` ascending (null last),
`created_at` oldest, `identifier`. Retry backoff: clean exit → fixed `1000` ms;
failure → `min(10000 * 2^(attempt-1), agent.max_retry_backoff_ms)`. No free
slot → requeue with `no available orchestrator slots`. Stall detection kills a
worker idle longer than `stall_timeout_ms`. Tracker refresh: terminal → stop and
clean workspace; neither active nor terminal → stop without cleanup; refresh
failure → keep running. Startup removes workspaces of terminal issues.

### Spec §9 Workspace management and safety

Workspace path `<workspace.root>/<sanitized_identifier>`, reused across runs,
not deleted on success. Population (checkout, bootstrap) is
implementation-defined, usually via hooks run with `sh -lc` in the workspace.
Three safety invariants: (1) launch the agent only with `cwd == workspace_path`;
(2) the workspace path must lie inside the workspace root after absolute
normalization; (3) workspace keys contain only `[A-Za-z0-9._-]`.

### Spec §10 Agent runner protocol

Launch `bash -lc <codex.command>` in the workspace; line-delimited JSON on
stdout, stderr is diagnostics only; 10 MB max line recommended. Handshake:
`initialize` → `initialized` → `thread/start` (approvalPolicy, sandbox, cwd) →
`turn/start` (threadId, input, cwd, title `<identifier>: <title>`,
approvalPolicy, sandboxPolicy). Completion: `turn/completed` success;
`turn/failed`, `turn/cancelled`, turn timeout, or subprocess exit are failures.
Emitted events include `session_started`, `turn_completed`, `turn_failed`,
`turn_input_required`, `approval_auto_approved`, `unsupported_tool_call`,
`malformed`. Approval and user-input requests must never stall a run; each
implementation documents its policy. Example high-trust policy: auto-approve
commands and file changes for the session; treat user-input-required as hard
failure. Unsupported dynamic tool calls (`item/tool/call`) return a failure and
the session continues. Optional client-side tool `linear_graphql`: one GraphQL
operation per call (`query`, optional `variables`), executed with Symphony's own
Linear auth so the agent never reads raw tokens. A request for user input
(`item/tool/requestUserInput`) fails the attempt immediately. Error categories
include `codex_not_found`, `invalid_workspace_cwd`, `response_timeout`,
`turn_timeout`, `turn_input_required`.

### Spec §11 Issue tracker contract

Required operations: `fetch_candidate_issues()`,
`fetch_issues_by_states(state_names)`, `fetch_issue_states_by_ids(issue_ids)`.
Linear: GraphQL, `project_slug` → `slugId`, page size `50`, timeout `30000` ms;
`blocked_by` from inverse `blocks` relations. Errors include
`missing_tracker_api_key`, `linear_graphql_errors`, `linear_missing_end_cursor`.
Tracker writes stay with the agent's tools, not the orchestrator.

### Spec §12 Prompt construction

Strict variable and filter checking; pass `attempt` so the prompt can differ for
first run, continuation, and retry. Render failure fails the attempt.

### Spec §13 Logging and observability

Logs carry `issue_id`, `issue_identifier`, `session_id`, stable `key=value`
phrasing. Optional runtime snapshot: running rows with `turn_count`, retry rows,
`codex_totals` (input/output/total tokens, `seconds_running`), latest rate
limits. Token accounting prefers absolute thread totals
(`thread/tokenUsage/updated`) and ignores delta payloads. Humanized event
summaries are observability-only; logic must not depend on them.

## Building and releasing

- Reference implementation in Elixir, chosen for concurrency and supervision
  primitives; the authors argue that when code is nearly free, languages can be
  picked for strengths. Readers are encouraged to point a coding agent at the
  spec.
- Version 1 was a Codex session in tmux polling Linear and spawning subagents;
  unreliable. Version 2 lived in the main agent-friendly repo. Then Symphony was
  used to build Symphony.
- Internal adoption spread after demos showing tasks with proof-of-work videos;
  internal product-market fit is a prerequisite for external launch at OpenAI.
- Codex implemented the Elixir version in one shot from `SPEC.md`. To polish the
  spec, Codex implemented it in TypeScript, Go, Rust, Java, and Python, and the
  results exposed ambiguities; it succeeded in every language.
- Incidental complexity removed: dependence on internal repos and on Linear MCP.
  Core rule: for every open task, guarantee an agent runs in its own workspace.
- The previously implicit human development workflow (take issue, check out
  repo, set In Progress, add PR, move to Review, attach videos) is now written
  in `WORKFLOW.md`, and Symphony makes agents follow it.
- Codex app-server mode (headless, JSON-RPC) was preferred over driving the CLI
  or tmux. Dynamic tool calls expose `linear_graphql` so the Linear access token
  is not exposed to subagents or containers and MCP is not needed.

## What's next

- Symphony is intentionally minimal and a reference implementation; OpenAI does
  not plan to maintain it as a product. The authors expect the bottleneck at
  other companies to shift from writing code to managing agentic work.
- Community: over 15K GitHub stars as of April 23; community ports include a Go
  TUI version and forks running Claude Code with GitHub Issues.

## Intro

- Five-month experiment: build and ship an internal beta product with **0
  lines of manually-written code**. The product has internal daily users and
  external alpha testers. Codex wrote everything: app logic, tests, CI config,
  docs, observability, internal tooling.
- Estimated build time: about **1/10th** of hand-writing. Motto: "Humans
  steer. Agents execute."
- The constraint was deliberate, to force building what raises velocity by
  orders of magnitude. Weeks to ship what became ~1M lines of code.
- The engineering team's job shifts to designing environments, specifying
  intent, and building feedback loops so Codex agents do reliable work. The
  scarce resource is human time and attention.

## We started with an empty git repository

- First commit: late August 2025. Initial scaffold (repo structure, CI,
  formatting rules, package manager, app framework) generated by **Codex CLI
  using GPT-5**, guided by a few existing templates. The initial `AGENTS.md`
  was also written by Codex. No human-written code anchored the system.
- After five months: ~1M lines across app, infra, tooling, docs, dev
  utilities. ~**1,500 PRs** opened and merged by **three engineers** driving
  Codex: average **3.5 PRs per engineer per day**. Throughput rose as the team
  grew to **seven engineers**. Hundreds of internal users, including daily
  power users.
- Core team philosophy: no manually-written code.

## Redefining the role of the engineer

- Early progress was slower than expected because the **environment was
  underspecified** (missing tools, abstractions, internal structure), not
  because Codex was incapable. The team's main job became enabling agents.
- Method: work depth-first — break goals into building blocks (design, code,
  review, test), have the agent build them, use them for harder tasks. On
  failure the fix is almost never "try harder"; ask what capability is
  missing and how to make it legible and enforceable for the agent.
- Humans work almost only through prompts: describe a task, run the agent, let
  it open a PR. To finish a PR, Codex reviews its own changes locally, requests
  further agent reviews locally and in the cloud, answers human/agent
  feedback, and loops until all agent reviewers are satisfied (a "Ralph Wiggum
  Loop"). Codex uses standard tools directly: `gh`, local scripts,
  repository-embedded skills.
- Humans may review PRs but are not required to; almost all review moved to
  agent-to-agent.

## Increasing application legibility

- With higher throughput, the bottleneck became **human QA capacity**. Fix:
  make the app UI, logs, and metrics directly legible to Codex.
- App bootable **per git worktree**, so Codex runs one instance per change.
  **Chrome DevTools Protocol** wired into the agent runtime, with skills for DOM
  snapshots, screenshots, and navigation; Codex reproduces bugs, validates
  fixes, and reasons about UI behavior.
- Observability: logs, metrics, traces exposed via a local, **ephemeral
  per-worktree observability stack**, torn down when the task ends. Agents
  query logs with **LogQL** and metrics with **PromQL**. Prompts like "service
  startup under 800ms" or "no span in four critical user journeys exceeds two
  seconds" become tractable.
- Single Codex runs often work on one task for **upwards of six hours**, often
  while humans sleep.

## We made repository knowledge the system of record

- Context management is a top challenge. Lesson: give Codex a map, not a
  1,000-page manual.
- The "one big `AGENTS.md`" approach failed because:
  - context is scarce — a giant file crowds out task, code, and docs; the
    agent misses constraints or optimizes for wrong ones;
  - too much guidance becomes non-guidance — when all is important, agents
    pattern-match locally instead of navigating;
  - it rots instantly — stale rules, agents can't tell what is true, humans
    stop maintaining it;
  - it is hard to verify — a blob resists mechanical checks (coverage,
    freshness, ownership, cross-links).
- So `AGENTS.md` is a table of contents (~**100 lines**) injected into
  context, pointing to a structured `docs/` directory that is the **system of
  record**.
- Layout: `AGENTS.md`, `ARCHITECTURE.md`, `docs/` containing `design-docs/`
  (`index.md`, `core-beliefs.md`, ...), `exec-plans/` (`active/`,
  `completed/`, `tech-debt-tracker.md`), `generated/` (`db-schema.md`),
  `product-specs/` (`index.md`, `new-user-onboarding.md`, ...), `references/`
  (`design-system-reference-llms.txt`, `nixpacks-llms.txt`, `uv-llms.txt`,
  ...), plus `DESIGN.md`, `FRONTEND.md`, `PLANS.md`, `PRODUCT_SENSE.md`,
  `QUALITY_SCORE.md`, `RELIABILITY.md`, `SECURITY.md`.
- Design docs are catalogued and indexed with verification status and core
  beliefs (agent-first operating principles). Architecture doc maps domains
  and package layering. A quality document grades each product domain and
  layer and tracks gaps over time.
- Plans are first-class: lightweight ephemeral plans for small changes;
  **execution plans** with progress and decision logs checked into the repo
  for complex work. Active plans, completed plans, and tech debt are
  versioned and co-located, so agents need no external context.
- Result: **progressive disclosure** — small stable entry point, then pointers.
- Enforced mechanically: linters and CI jobs check the knowledge base is
  current, cross-linked, and well-structured. A recurring **"doc-gardening"
  agent** finds stale docs that do not match code behavior and opens fix-up
  PRs.

## Agent legibility is the goal

- The repo is optimized first for Codex's legibility, so an agent can reason
  about the full business domain from the repo alone.
- Anything the agent cannot access in-context at runtime effectively does not
  exist. Google Docs, chat threads, and people's heads are invisible; only
  repo-local versioned artifacts (code, markdown, schemas, executable plans)
  count. A Slack discussion that settled an architecture pattern is illegible
  unless it is in the repo.
- More context means organizing and exposing the right information, not more
  ad-hoc instructions; onboard the agent like a teammate (product principles,
  engineering norms, team culture).
- Tradeoffs: prefer dependencies and abstractions the agent can fully
  internalize in-repo. "Boring" technologies are easier for agents to model
  (composability, API stability, training-set representation). Sometimes it
  is cheaper to have the agent reimplement a subset than work around opaque
  upstream behavior: e.g. an in-house map-with-concurrency helper instead of a
  generic p-limit-style package, integrated with OpenTelemetry and at 100%
  test coverage.
- This leverage also helps other agents on the codebase (e.g. Aardvark).

## Enforcing architecture and taste

- Docs alone do not keep an agent-written codebase coherent. Enforce
  **invariants, not implementations**: e.g. Codex must parse data shapes at
  the boundary, but the library is not prescribed (the model tends to pick
  Zod).
- Rigid architecture: each business domain has a fixed set of layers with
  validated dependency directions and limited permitted edges. Within a domain
  (e.g. App Settings) code depends only forward through **Types → Config →
  Repo → Service → Runtime → UI**. Cross-cutting concerns (auth, connectors,
  telemetry, feature flags) enter only through one explicit interface:
  **Providers**. Everything else is disallowed and mechanically enforced via
  Codex-written custom linters and structural tests.
- Such architecture is usually deferred until hundreds of engineers; with
  coding agents it is an early prerequisite that allows speed without drift.
- "Taste invariants" enforced statically: structured logging, naming
  conventions for schemas and types, file size limits, platform-specific
  reliability requirements. Custom lint **error messages carry remediation
  instructions** into agent context.
- Model: enforce boundaries centrally, allow autonomy locally (like a platform
  org). Output need not match human style if correct, maintainable, and
  legible to future agent runs.
- Human taste flows back continuously: review comments, refactor PRs, and
  user-facing bugs become doc updates or tooling. When docs fall short, the
  rule is promoted into code.

## Throughput changes the merge philosophy

- Minimal blocking merge gates; short-lived PRs; test flakes often handled by
  re-runs rather than blocking. When agent throughput far exceeds human
  attention, corrections are cheap and waiting is expensive. The author notes
  this would be irresponsible in a low-throughput setting.

## What "agent-generated" actually means

- Agents produce: product code and tests; CI config and release tooling;
  internal dev tools; docs and design history; evaluation harnesses; review
  comments and responses; repo-management scripts; production dashboard
  definition files.
- Humans stay in the loop at a higher level: prioritize work, turn user
  feedback into acceptance criteria, validate outcomes. Agent struggle is a
  signal to add missing tools, guardrails, or docs — always written by Codex.
- Agents pull review feedback, respond inline, push updates, and often squash
  and merge their own PRs.

## Increasing levels of autonomy

- The repo recently crossed a threshold: from one prompt Codex can drive a new
  feature end-to-end: validate codebase state; reproduce a reported bug;
  record a video of the failure; implement a fix; validate by driving the app;
  record a second video of the fix; open a PR; respond to agent and human
  feedback; detect and fix build failures; escalate to a human only when
  judgment is needed; merge.
- Caveat: depends heavily on this repo's structure and tooling; do not assume
  it generalizes without similar investment, "at least, not yet".

## Entropy and garbage collection

- Codex replicates existing patterns, including uneven or poor ones, causing
  drift. The team once spent every Friday (**20% of the week**) cleaning "AI
  slop"; that did not scale.
- Fix: encode **"golden principles"** in the repo plus a recurring cleanup
  process. Examples: (1) prefer shared utility packages over hand-rolled
  helpers to centralize invariants; (2) no "YOLO-style" data probing —
  validate boundaries or use typed SDKs so the agent cannot build on guessed
  shapes.
- Background Codex tasks on a regular cadence scan for deviations, update
  quality grades, and open targeted refactor PRs; most are reviewable in under
  a minute and automerged.
- Framed as garbage collection: tech debt is a high-interest loan, best paid
  continuously in small increments. Human taste is captured once and enforced
  on every line; bad patterns are caught daily.

## What we're still learning

- Worked through internal launch and adoption at OpenAI.
- Unknowns: how architectural coherence evolves over years in a fully
  agent-generated system; where human judgment adds most leverage and how to
  encode it; how the system changes as models improve.
- Conclusion: discipline moves from the code into the scaffolding (tooling,
  abstractions, feedback loops). Hardest problems: designing environments,
  feedback loops, and control systems for agents.
